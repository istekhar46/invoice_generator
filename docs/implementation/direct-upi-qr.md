## A. Original requirements

The user deferred invoice date consistency and accepted the next recommendation with **“start”**: businesses save their UPI ID and payee name; eligible INR invoices and PDFs display a direct UPI payment QR; owners confirm receipts through the existing **Record UPI payment** flow. Scanning does not mark an invoice paid. Keep the current single-account model, existing Razorpay checkout/ledger/stock contracts, and the date correction deferred.

Scope: signed-in payment preferences, invoice payment controls, shared invoice preview/public page/PDF rendering, additive database changes and local verification. Reuse the existing local QR encoder. No automatic receipt confirmation, bank account setup, new payment gateway, payment probe, messaging, live migration/deployment or PR publication is part of this implementation request.

Subsequent authorization: **“push and create pr”** authorizes committing/pushing this implementation and its retained release notes, then opening a PR into `dev`. Merge, hosted migration and deployment remain outside that publication request.

Acceptance: account-isolated validated preferences; eligible issued INR invoices expose the correct payee, outstanding amount and invoice reference; no payment instructions on drafts/paid/voided/non-INR invoices or quotations; QR decoding matches the intended UPI payload; payment/status/stock change only through existing explicit workflows. Preserve invoice financial snapshots and current public-sharing access controls.

**Confirmed owner decisions:** explicitly enable direct UPI per issued invoice and preserve its saved payee details when account preferences change. One collection route per invoice: cancel any active/unresolved Live Razorpay link before enabling direct UPI, and remove direct UPI before creating a Live Razorpay link. Test mode retains its existing isolation. Questions were answered before dependent implementation.

## B. Technical assessment

- Payment settings retains its separate Razorpay Test/Live connection forms and now includes an independent direct-UPI preference section. Saving a UPI ID requires no gateway credentials and makes no provider-verification claim.
- Reuse `paymentQrDataUrl`, invoice preview/PDF mapping and the existing manual UPI ledger. No new QR library or automatic payment source is needed.
- `InvoiceService.findById`/list and public sharing now expose a restricted nested `directUpi` snapshot alongside the existing Live checkout contract. The owner can remove retained details even when paid/voided/non-INR; public reads omit receiving instructions when not payable. Public reads never pull account-wide preferences or expose owner/internal IDs.
- `GatewayService.create` and payment mutations already lock the invoice. Reuse that lock for route changes, with consistent lock ordering; unresolved remote links are detected using the existing `activeKey` contract. Test-mode payments remain financially isolated.
- Invoice QR amounts must use the saved invoice balance and two-decimal INR precision. Payee text and invoice references must be encoded as query values, not concatenated into raw URI syntax. Syntax validation does not verify ownership, bank acceptance or settlement. Printed PDFs are static and a direct UPI payload cannot be remotely revoked.
- Official [Google Pay UPI field documentation](https://developers.google.com/pay/india/api/web/create-payment-method) confirms payee/name/reference/note and INR amount semantics; its Web PaymentRequest integration is separate and was not added. The linked NPCI specification currently serves an HTML application rather than the historical PDF; generic payload evidence was verified using the primary source below. No merchant category, signature or provider parameters were invented.
- Google's [January 2025 W3C presentation](https://www.w3.org/2025/Talks/google-paymentlink-20250130.pdf), slide 9, explicitly illustrates a generic `upi://pay?pa=…&pn=…&am=…&cu=INR` QR payload. Use those fields with a random public invoice payment reference and bounded invoice note. Do not add browser facilitated-payment APIs, guessed MCCs or signatures. Decode real output independently; actual bank/app acceptance remains a separate manual check.
- Existing `.env`/merchant credentials and ignored release artifacts are outside feature inputs. Preserve existing local docs changes from the prior completed release.
