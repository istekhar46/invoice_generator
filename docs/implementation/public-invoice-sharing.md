## A. Original requirements

After payment panel/QR PR #21 was merged/deployed, the owner asked for the next task and then **“start”** on this proposal:

- A customer opens a secure public link without signing in, views the invoice/current balance, downloads its PDF and pays through the existing Razorpay checkout.
- The signed-in owner can copy a share link and revoke it.
- Public responses contain only customer-facing invoice details.
- Document the implementation before changing feature code. Keep this increment minimal and reuse the existing invoice/PDF/payment flows.

Exclusions: public editing or payment recording, creating checkout links from public access, customer accounts, email/WhatsApp/SMS, reminders, direct UPI-ID QR, new payment providers/sources, attachments, quotations and guest-draft sharing. The subsequent request authorizes publishing a PR into `dev`, without merging, hosted migration, deployment or real payment. Use Render CLI instead of browser control for future Render work; no Render access is needed to publish this PR.

### Confirmed business decisions

The owner confirmed all three recommended policies before dependent implementation:

1. New shares may be created only for issued Sent/Paid invoices; drafts remain private.
2. Existing shares show current details/balance and a cancellation notice after void. Owners may still copy/revoke an existing voided share, but cannot create a new one for a voided invoice.
3. Shares remain valid until revoked; no automatic expiry. Revoking and re-enabling yields a different link.

Acceptance requires owner isolation, repeatable copy/reuse, revocation and a different link after re-enabling; current balances and only the existing eligible Live checkout URL; invalid/revoked links with no invoice disclosure; public preview/PDF/mobile/error states; and no payment, status, stock or messaging effect from opening/downloading a document. Downloaded PDFs and already-open pages cannot be remotely erased after revocation; subsequent reads/downloads must recheck access.

## B. Technical assessment

### Verified repository contracts

- Nest11/Prisma7/PostgreSQL API, React19/Router7/Query5 frontend. `@nestjs/jwt`11 is already installed; no new runtime dependency is needed.
- `InvoiceService.findById` and `invoicePaymentUrl` select the current active Live link for an enabled merchant, matching a positive Sent INR balance. Test URLs and paid/voided invoices are excluded. No provider calls are needed for public reads.
- The existing owner invoice DTO includes customer IDs, timestamps and internal relationships. It must not become the anonymous response. Standard invoices use the current company/customer profile; quick invoices use their saved party snapshots. Preserve those existing document semantics and saved financial/line amounts.
- `InvoicePreview`, `documentTotals`, `pdfGenerator.service` and `InvoicePDFTemplate` provide shared document/PDF/checkout-QR rendering. A bounded public document adapter can reuse them without exposing owner controls or changing ledger logic.
- `@Public()` bypasses the global JWT guard; the global rate limiter remains. `LoggingInterceptor`, `TransformInterceptor` and `GlobalExceptionFilter` include request URLs in logs/responses. Therefore do not send the share secret in API paths/query strings.
- `MainLayout` initializes owner authentication/navigation. The customer page needs a separate router branch, accessible to signed-in and signed-out viewers, without owner queries/sidebar or login redirects.
- Assessment found that successful development request/response logging ignored `apiClient.sensitive`. This is now corrected and tested. Public reads use a credential-free fetch call without owner tokens, authentication refresh or shared query-cache persistence.
- API locking already uses `lockInvoiceRow` for lifecycle/financial mutations. Use that boundary for owner share create/revoke so concurrent requests and invoice-state changes have a defined order. Public document reads must select the capability and current invoice/payment data in one database snapshot.

### Chosen technical approach

1. **Capability, not account authentication:** use the existing Nest JWT library with a dedicated server-only `INVOICE_SHARE_SECRET` (32 random bytes, canonical base64), fixed HS256, issuer and audience. Payload contains only a cryptographically random 32-byte share ID, not invoice/account/customer IDs. An active database row maps that ID to its owned invoice. Repeated copies reproduce the signed link; revocation deletes the mapping and a later explicit create uses a fresh random ID. No usable bearer token is stored and account/payment credential keys are not reused. There is no automatic expiry, as confirmed by the owner.
2. **Additive storage:** one active share per invoice with an account-bound invoice relation and creation time. No invoice backfill, financial rewrite or new payment table. Rehearse an additive SQL upgrade and fresh-schema path locally; do not apply it to hosting in this task.
3. **Owner API:** authenticated status/create-or-reuse/revoke under `/invoices/:id/share`. Status exposes availability/active state; only explicit create/copy commands return the sensitive token. POST requires strict boolean `createIfMissing`: true for explicit creation, false for copying an existing link. A stale copy cannot reactivate a revoked share; it returns409 and requires reloading settings before explicit creation. Creation/revocation do not alter invoice/payment/stock values. Missing server configuration disables sharing with an actionable setup state; malformed nonempty configuration fails startup. Keep the key stable: rotation invalidates old signatures, and owners must copy a newly signed URL or revoke/create a replacement. No old-key fallback is implemented.
4. **Customer API:** `GET /public/invoice`, with the share token in `Authorization`, explicit restricted projection, no account-auth requirement and existing rate limiting. Uniform unavailable response for invalid/deleted/revoked capability; `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex, nofollow, noarchive` for success and errors. Apply the confirmed invoice-state policy server-side. No create/mutate/provider endpoint is public.
5. **Customer URL:** `/shared/invoice#<token>`. URI fragments are not sent in HTTP requests, so the capability avoids frontend/backend access-log URLs. The page sends it only in the public read Authorization header, with credentials omitted, no-store and no-referrer. No token/invoice persistence in local/session storage or owner query cache. Document title/robots/referrer metadata is generic and excludes customer/invoice details.
6. **UI/PDF:** owner panel beside existing invoice payment controls; explicit copy/create and confirmed revoke, clipboard failure with manual-copy access and clear bearer-link notice. Standalone customer document with status/current balance, refresh, fresh-authorized PDF download and existing eligible checkout/QR. Race handling must discard prior-token results and remove stale checkout while refreshing. Recheck public access before PDF generation; retain the existing clickable URL for same-device use.

The implemented public projection excludes account identity, user/customer/catalog IDs, source quotation, client request IDs, merchant/provider identifiers/secrets, stock and payment-history details. Its document ID identifies the share for rendering and reveals no underlying invoice ID. Quick parties retain their saved snapshots; standard parties follow existing current-profile semantics. Missing logo values are normalized to the public document contract. Real API tests cover both workflows and private-field exclusion.

### Evidence and rationale

- [Nest JWT](https://github.com/nestjs/jwt/blob/master/README.md) and [jsonwebtoken](https://github.com/auth0/node-jsonwebtoken/blob/master/README.md) support per-call secrets, fixed algorithms and issuer/audience verification. A local probe against the installed library confirmed repeatable signed links without timestamp, random share-ID round trip and rejection under the wrong issuer/audience. No secret/token was printed.
- [Node22 crypto](https://nodejs.org/docs/latest-v22.x/api/crypto.html) supplies the CSPRNG. [OWASP cryptographic storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) supports keeping keys separate from stored data. Using an independent signing key plus an active random mapping avoids storing recoverable bearer tokens or introducing a second encryption implementation.
- [MDN URI fragments](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Fragment) confirms fragments are not sent to servers. The fragment transport is our design inference from that behavior and the repository's URL logging, not a claim that browser history/bookmarks are private.
- OWASP's [URL-token guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) supports strong randomness, rate limits and no-referrer. Its reset-token single-use/short-expiry rules do not define the lifetime of this repeatedly viewed invoice capability; the owner explicitly chose validity until revocation.

Risks/limits: anyone holding an active link can read the displayed invoice; forwarded links remain bearer access. Already-downloaded PDFs are static. Revoking a share does not cancel its independently managed Razorpay checkout URL. Profile changes continue to affect standard invoice rendering as they do today; adding issued-invoice party snapshots is outside this increment. No physical scan, actual Live checkout/settlement or hosted sharing flow was tested; provider states were controlled local fixtures.

**Existing date issue requiring a separate rule:** `InvoiceBuilder` uses UTC date-input values, while `QuickInvoiceBuilder` parses local midnight; shared `formatDate` displays dates in the viewer's timezone. Reproduction: stored `2026-11-05T00:00:00Z` displays Nov5 in Kolkata and Nov4 in Los Angeles. Public sharing preserves this existing behavior and does not rewrite dates. Normalizing historical quick timestamps requires an agreed timezone/date-only migration rule; blindly formatting everything as UTC could change their intended day. Evidence: `existing-date-finding.json` in the private artifact directory. Do not claim cross-timezone calendar-date consistency until that separate correction is agreed and verified.
