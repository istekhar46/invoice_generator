### Simple document rules — DEC-02 (later increments)

- New automatic numbers: atomic per-account sequences `INV-000001` and `QT-000001`, without annual reset/settings. Preserve existing/custom invoice numbers and editable invoice numbering; generated numbers skip collisions. Database uniqueness handles concurrency; deleted/cancelled numbers are not reused.
- Quotation states: Draft, Issued, Accepted, Declined, Cancelled. Issued is a manual action, not proof of sending. Display expiry from validity date without a scheduler. Owner records acceptance/decline; no customer portal.
- Draft content is editable; issued commercial content is fixed. Cancel and create a fresh quotation for revisions. Expired/cancelled/declined quotations cannot convert.
- Convert an accepted quotation **in full, once, to one draft invoice**, with target review before save. Preserve source/links and financial snapshots; invoice has its own number, reviewed dates, and zero inherited payment. Atomic/idempotent conversion returns the same target on retries. No partial billing, quotation deposits, or quotation-to-order/pro-forma flow.
- Reuse invoice Draft/Sent/Paid. “Issue invoice” maps to Sent without sending. Add an explicit auditable **Voided** state for unpaid issued invoices: cancel active links, reverse stock once, retain number/history, exclude from active totals. Paid/part-paid invoices require payment reversal/refund before voiding. Delete only drafts without stock/payment history. This deliberately replaces unrestricted deletion/status reversal where posted history exists.
- Preserve existing invoice edit rules: pricing changes recalculate, detail-only edits retain saved amounts, and a Paid invoice with positive balance returns to Sent. Resolve active links before financial changes; quantity edits post only net stock differences. Moving an issued invoice back to Draft is replaced by explicit voiding.

### Product/service catalog and legacy migration

- One account-owned catalog: Product/Service kind, name/description, optional SKU, unit, selling price/currency, active/archive state. Retain invoice-level tax. No purchase price, media, variants, barcode tooling, price lists, or category hierarchy now.
- Both signed-in editors search/select an item or create it inline. Selection copies editable description/unit/rate into the document snapshot. Validate ownership/active state. If currencies differ, require an explicit invoice-currency price; no silent FX conversion.
- One-off charges remain possible as Product/Service without saving a catalog item; unlinked rows do not track stock. Catalog creation is explicit, not a typing side effect. Guests continue with local one-off rows.
- Migrate persisted MATERIAL → PRODUCT and LABOR → SERVICE using stored type, preserving row descriptions/units/quantities/rates/amounts and invoice totals/numbers. Do not infer types/identity from descriptions or merge historical rows into catalog items. Previously overwritten labor types cannot be reconstructed by guessing.
- Old rows keep snapshots with an optional empty catalog reference. Catalog edits/archive cannot rewrite saved documents. Retain archived references on existing rows but reject new selection. Kind/unit become fixed once referenced. Products may opt into tracking later with a current-stock opening balance; tracking then stays enabled and its unit/kind/start marker stay fixed. Archive retires an item.
- Update schema/DTOs, API/frontend types, both transformers, form/calculation guards, editors, previews/PDFs, fixtures, and directly affected stale copy/docs together. Retire unused labor-rate contracts after verifying callers; document any column removal in the reviewed migration.
- Normalize known legacy guest draft types once **before validation**, retain values/idempotent import, and persist the normalized draft. Import creates no catalog/stock history automatically. This is a scoped data upgrade, not an indefinite legacy write path.

### Inventory research and recommendation — DEC-07

Research distinguishes goods/services from optional goods inventory; services have no stock. Invoice-based stock and physical shipment stock are separate concepts in [Zoho item setup](https://www.zoho.com/in/inventory/help/items/items-overview.html) and [stock tracking methods](https://www.zoho.com/us/inventory/help/items/item-details.html).

**Recommendation:** invoice-based quantity tracking in one stock pool. This fits our invoice flow while purchases, fulfillment, warehouses, and accounting are deferred. Do not present it as physical fulfillment or inventory valuation.

1. Tracking is optional/off by default for products; never enabled for services/unlinked charges. Set a non-negative opening quantity for a newly tracked product. Manual Stock In/Out requires date/reason; these are quantity adjustments, not purchase/expense/payment records.
2. One base unit per item, positive sale quantities, fixed decimal precision, no unit conversions. Reject negative resulting stock with available quantities/conflicting items. Specify matching quantity precision/bounds in DB/DTO/form contracts before code.
3. Drafts/quotations do not consume/reserve stock. Deduct once when the owner issues the invoice (Draft → Sent). New receipt/link actions require issue first, so payment cannot arrive before stock is checked/booked. Repeated status/payment events do not deduct again. Imported historical paid amounts remain migration balances, not new payment actions.
4. Issued-invoice edits compare old/new tracked quantities **grouped by catalog item**, applying only the delta with the invoice update atomically. Price-only edits, PDFs, previews, and catalog edits cause no movement. Voiding reverses posted quantities once.
5. Append-only history records item/time/delta/source/actor/reason/reversal reference. Ledger is authoritative; cached balances must reconcile. Use transactions/concurrency control per product and unique source actions to prevent overselling/double posting. Do not rely on invoice-row IDs, which currently change on edits.
6. Cut over from owner-entered opening quantities. **Never replay historical invoices as deductions.** Migrated invoices/rows stay outside automatic stock posting; new catalog-linked invoices issued after cutover participate. Guest imports are drafts: consume only after explicit catalog selection/issue. Explain this boundary in rollout/UI notes.
7. No warehouses/transfers, committed stock, backorders, FIFO/average costing, valuation, lots/serials, bundles, or automatic purchase/return posting. Physical returns use explicit quantity adjustments; payment refunds do not prove returned goods and cannot automatically restock.

Swipe's authenticated [product catalog](https://app.getswipe.in/products) exposes Product/Service, price/unit, optional opening quantity, and further inventory controls. Its richer tax/purchase/media/batch fields are deliberately excluded here.

### UPI receipts and Razorpay links

**Records and currency.** New payment actions are UPI/INR and require an issued, non-void invoice with a positive balance. Existing multi-currency invoices retain view/edit/PDF and historical balances; no other payment method/FX is added. “Record UPI payment” captures date, amount, optional transaction reference, notes. Distinguish owner-recorded receipts from gateway-verified ones. One receipt applies to one invoice; no wallet/cross-invoice allocation UI.

**Balance authority.** Derive paid amount server-side from opening baseline + applied receipts − reversals/refunds. Existing `amountPaid` response becomes derived/cache, not another editable source. Replace free aggregate edits/Mark Paid assignments with Record payment, which pre-fills balance for explicit owner confirmation. Guest local paid-amount editing remains. On import, guest-entered amounts become labeled owner-provided opening balances, not verified UPI transactions.

Receipts/adjustments are not overwritten or deleted. Owners correct manual entries with a linked reversal/reason; this records bookkeeping, not a transfer of money. Gateway receipts change only after verified provider state/refund confirmation, not an owner's manual edit.

**Existing data.** Preserve existing paid amounts in each invoice's currency as labeled opening balances, none for zero. Historical method/payment date remain unknown; migration time is not payment date. Reconcile existing balances/statuses before deriving statuses. Refunds/reversals reopen balances without silently repricing invoices.

**Connection.** Use the official [Razorpay Node SDK](https://github.com/razorpay/razorpay-node/blob/master/documents/paymentLink.md). Each business connects its own test/live credentials and webhook secret through authenticated setup. Validate connection; encrypt secrets server-side, mask reads, never return/log secrets, keep Test/Live separate. Resolve callbacks from stored connection/link/payment ownership, not a supplied user ID. No platform collection, partner onboarding, split settlement, or payouts.

**Link choice.** Dedicated [UPI Payment Links](https://razorpay.com/docs/payments/payment-links/upi/) are documented as Android-only, Live-only, without partial payments. Recommend [Standard Payment Links](https://razorpay.com/docs/payments/payment-links/standard/) configured UPI-only; [SDK method controls](https://github.com/razorpay/razorpay-node/blob/master/documents/paymentLink.md) support checkout customization. Verify actual Test-mode desktop/mobile behavior and separately authorized Live readiness. Never silently enable other methods if UPI configuration fails.

- Link amount equals current INR balance; provider partial payments disabled for simplicity. Manual UPI receipts can be partial. One active link per invoice; repeat requests reuse it. Resolve ambiguous API timeouts via provider reference before another create attempt.
- Actions: create/copy/open, status, cancel, authenticated refresh. Saved invoice/PDF can include active Pay via UPI URL. Customer uses Razorpay-hosted checkout; no new public invoice portal. Disable provider SMS/email/reminders; sending is deferred.
- Resolve provider payment/cancellation state before amount/currency edits, manual receipts, or voiding. Failed synchronization preserves state and shows an actionable error; stale/cancelled links cannot be shown as active.
- Only verified captured/paid funds create a gateway receipt; validate merchant/method/currency/amount/linkage/provider IDs. Redirects, screenshots, entered references, and link creation cannot mark gateway-paid.
- Verify signature on **raw request body**, deduplicate events/payments, handle out-of-order events, and atomically persist receipt/application/invoice state. Add authenticated provider refresh for missed events. See [webhook validation](https://razorpay.com/docs/webhooks/validate-test/) and [payment-link events](https://razorpay.com/docs/payments/payment-links/subscribe-to-webhooks).
- Retain all verified funds even when a concurrent payment leaves excess. Apply no more than invoice balance; show received/applied/excess and an owner-visible exception instead of dropping funds/exceeding the paid cap. A late payment against a void invoice remains unapplied with an alert; it cannot silently reopen the invoice or deduct stock. Refund initiation stays in Razorpay. Sync [processed refunds](https://razorpay.com/docs/payments/refunds/subscribe-to-webhooks) as traceable adjustments; pending/failed refunds do not prematurely reduce paid amounts. Credit notes/refund initiation UI/automatic refunds are deferred.
- No bank form/ledger inside our app. Merchant activation/KYC and settlement-bank setup still happen with Razorpay: deferring our bank module does not remove provider prerequisites. See [Razorpay setup](https://razorpay.com/docs/payments/set-up).
